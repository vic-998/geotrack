做地图、出行、物联网，或者任何和位置有关的业务，GPS 轨迹通常都不是拿来就能用。GeoTrack 想做的，是把这些经常重复实现的基础能力，整理成一个小而实的 Java 工具库。

一、GPS 轨迹为什么总要先处理一下

轨迹抖动

定位点有误差，直接连线容易来回摆动，速度和距离等指标也会跟着不稳定。

坐标不统一

WGS84、GCJ02、BD09 同时出现在数据链路里，叠到地图上可能发生偏移。

点太多

整段轨迹可能有几万个点，传输、存储和渲染都要付出成本。

格式太杂

KML、GPX、坐标串、Encoded Polyline，各自有不同的编码和结构。

最开始，大家可能只是想把线画出来。后来才发现，轨迹能画出来，不代表它已经能拿来做业务。

轨迹处理的目标，不是把点删得越少越好，而是在保留形状和顺序的前提下，让数据更稳定、更轻量、更容易使用。

二、GeoTrack 具体解决什么问题

输入

KML / GPX / Polyline

把不同来源的数据统一成 GeoPoint 轨迹点。

坐标

WGS84 · GCJ02 · BD09

统一坐标系，支持批量转换。

稳定

Kalman + RTS

在线滤波，离线平滑，让路线更稳。

压缩

DP · VW · LTTB

保留轨迹形状，减少传输和存储。

分析

Fréchet · Hausdorff · DTW

比较两条轨迹的相似程度。

空间

Geohash · 停留点

计算空间编码、中心位置与停留时长。

导入→解析→坐标转换→去噪→抽稀→空间分析→业务系统

三、它和一个完整地图 SDK 有什么区别

GeoTrack 不是地图 SDK，也不是一个带页面的轨迹管理系统。

它负责的是地图和业务系统之间的那一层：把原始位置数据处理成更可靠、更适合计算和传输的轨迹数据。

项目不需要 Spring，也不需要数据库，核心能力基于 JDK 和少量第三方库构建。模块以静态工具方法为主，没有隐藏状态，适合放进服务端、批处理程序、桌面工具，或者你自己的数据管道里。

算法边界也保持清楚：抽稀、滤波、坐标转换、解析和空间分析各自独立，出了问题容易定位，也方便替换参数。

四、几段代码，把一条轨迹处理完

比如，先从 GPX 读取轨迹，再做坐标转换、RTS 平滑，最后压到最多 500 个点：

var raw = GpxTrackParser.parse("route.gpx");
var converted = CoordinateTransform.transformBatch(raw);
var smooth = KalmanTrackSmoother.smooth(converted);
var ready = TrackSimplifier.simplify(smooth, 500, 5D);

没有 GPX，也可以直接解析坐标串：

var points = PolylineParser.parse(
    "39.9000,116.4000,50,39.9100,116.4100,52");

如果需要找出一条轨迹里的停留位置：

var stays = StayPointDetector.detectBySequence(points, 50D, 300D);

这些方法不会启动服务，也不会要求你先搭一套框架。对一个已经存在的 Java 项目来说，加入依赖、传入轨迹点，就可以开始处理。

五、为什么把它开源出来

轨迹处理看起来是基础能力，但它经常散落在不同项目里：一份坐标转换代码在服务 A，一份抽稀代码在服务 B，某个格式解析器又藏在另一个脚本里。

GeoTrack 想做的是先把这一层整理清楚：接口小一点，依赖少一点，算法说明和测试跟着代码走。你可以直接使用，也可以读源码、换参数、按自己的业务继续扩展。

写在最后

GeoTrack 做的事情不大：不替你画地图，也不替代完整 GIS 平台。

它只是把一条原始 GPS 轨迹，先处理成更稳定、更轻量、更适合分析的样子。

很多位置业务，真正需要的也许就是这一层基础能力。
